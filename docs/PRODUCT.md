## 范围与规范关系

本文记录 NarrateOS 的产品定位、目标用户和长期约束，以当前 Web 入口 Operator Studio（创作室）的使用场景为重点。CLI 是引擎的另一入口，不代表另一套产品规则。

## 目标用户

主要用户是熟悉 AI 工具的个人小说作者：能够配置模型，愿意监督连续生成，并在关键处审阅与干预。

用户在这里承担导演与作品负责人的角色，而不是通过一问一答累积聊天上下文。自动化承担重复执行、资料装配、审校与状态维护；作者掌握作品方向，并可选择逐章共驾或连续生成后的抽查修订。

## 产品目的与成功标准

NarrateOS 是通用长篇小说多智能体写作引擎。它将开书设定、章节规划、执笔、审校和跨章状态维护组织成可干预、可追溯的持续创作流程。

成功意味着：

- 作者能够从创作种子或既有设定建立作品工作区，并持续推进章节。
- 作者能够区分正在执行、等待介入、已落盘与发生冲突的状态，知道下一步可以做什么。
- 人工改稿与导演指令能够进入真实的作品状态，而不只是改变界面显示。
- 异常和自动修复边界可见，作品资产不会因界面刷新、连续运行或恢复流程而失去可追溯性。

以上是产品判断标准，不是已测得的质量、速度或商业收益承诺。

## 产品机制与定位

- 采用导演控制台而非聊天消息流：作者围绕作品、章节、运行状态和审阅结果开展工作。
- 以独立 Git 作品仓库和纯文本资产承载长期创作；定稿手稿是事实真源，实体档案与索引是派生视图。
- 通过职责分离的模型工序与确定性校验协作，减少对单个累积对话窗口的依赖。
- 将规划层的全知因果推演与写手可见事实隔离；原创建书与同人设定输入在初始化后使用统一运行时契约。
- 将可配置的文学选择与内核机制分开，不把题材分类、角色数量或经验预算固化为通用产品规则。

这些是本产品采用的机制，不构成对其他产品能力的比较结论，也不保证自动生成内容无需人工判断。

## 使用环境与主要工作流

当前 Studio 是运行于 DeepSeek Harness（dsh）Web 宿主内的 React 插件，不是独立部署的聊天网站。宿主提供模型配置、认证和 HTTP 服务等基础设施；Studio 通过 REST 与 SSE 获取操作结果和运行状态。

主要工作流：

1. 创建或切换作品，完成开书输入与引导。
2. 逐章推进，或启动 YOLO 连续生成；需要停止时在安全点收束运行。
3. 阅读正文、检查本章细纲与修改 Diff，查看作品派生视图和运行信息。
4. 通过一次性导演纸条影响后续生成；待消费纸条可以撤回。
5. 手工修改章节并同步派生状态，或触发 Dreaming 整理；遇到安全停机时查看冲突与隔离信息，再决定如何继续。

这套流程支持作者介入频率变化，不要求所有用户始终挂机，也不要求每章都手动批准。

## 能力与硬约束

- **作品资产隔离**：通用引擎仓库与具体作品物理隔离；每部作品使用独立的 `books/<slug>/` Git 子仓库。
- **手稿优先**：人工手稿修改经 Sync 刷新派生视图；历史修改的下游冲突应显式呈现，不能把静默改写后文当作同步。
- **事务与可追溯性**：正文和状态落盘遵循既定 WAL 与原子提交协议；界面反馈必须对应真实操作结果。
- **自治有边界**：自动回滚范围由配置控制；超出允许范围的冲突进入明确的安全停机路径，不以无提示的自动处理掩盖风险。
- **宿主边界**：`packages/core` 不依赖 `@deepseek-ai/*`；模型调用通过 `LlmPort`，宿主适配封闭在插件与预设层。复用宿主资源不意味着改动宿主源码。
- **模型输入隔离**：写手获得正向目标状态与可见事实；规划内部推演、未揭晓底牌和已废止的 `WARPED` 条目遵循既定隔离规则。
- **配置优于文学预设**：窗口预算、回滚范围、声纹标签、焦点人数和文风插件遵循已有可配置或模型自决契约。

## 产品原则

1. **作者掌舵，自动化执行**：减少重复劳动，同时保留对方向、成稿和异常处置的控制。
2. **真实资产优先于界面表象**：保存、撤回、同步与状态展示必须对应底层事实。
3. **长期一致性优先于单次生成**：围绕跨章事实、伏笔、视角和事务恢复组织工作，而不是只优化单次输出。
4. **明确边界优先于隐式接管**：让作者知道自动化做了什么、停在哪里、何时需要介入。
5. **通用机制优先于题材硬编码**：保持引擎、作品和宿主解耦，让具体文学选择留在作品配置与创作决策中。
